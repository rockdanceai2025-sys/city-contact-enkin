# LP制作 → パスワード付き確認公開 → 呼び出して修正

LPを作り、クライアントに安全に見せ、あとから直すまでの一連の流れを扱う。

## まず入口を見分ける

ユーザーの依頼は次の3つのどれか（複数のこともある）。該当する節に進む。

| 依頼の内容 | 進む先 |
| --- | --- |
| LPを新しく作る／構成案を形にする | **A. 制作** |
| 作ったLPをクライアントに見せる／URLを出す／PASSをかける | **B. 確認用公開** |
| 前に作ったLPを直す／続きをやる | **C. 呼び出し** |

「作って見せたい」ならA→B。「直して見せ直したい」ならC→A（修正）→B（再公開）。

---

## A. 制作

### A-1. 着手前に確認する

構成案（PDF・企画書・既存サイトのスクショ）を渡されたら、**まず全部読んでから**着手する。
そのうえで、読み取れなかった点だけを簡潔に質問する。よく詰まるのは次の4つ。

- **会社情報**：社名・屋号／電話番号／所在地／受付時間／許認可番号（古物商許可など）。
  未確定ならダミーで進めてよいが、**推測で埋めない**。郵便番号や番地を勝手に作ると誤情報になる。
  ダミーにした項目はREADMEに一覧化し、あとで一括置換できるようにする。
- **対応エリア・サービス名**：構成案と口頭指示が食い違うことがある。指示が新しい。
- **数字の出どころ**：料金表・実績・お客様の声。企画書の想定値か、実際の掲載値か。
  **既存サイトのスクショをもらったら、そこに載っている数字が実運用の値**である可能性が高い。
  企画書と食い違ったら、勝手に選ばず必ず食い違いを示して確認する。
- **置き場所**：既存リポジトリのサブフォルダか、新規リポジトリか。

質問は選択肢つきで一度にまとめて出す。答えが返らなくても、既定値を明示して進めてよい（後から直せる）。

### A-2. ファイル構成

1ページ完結の縦スクロール型。ビルドツールもフレームワークも使わない。
そのまま開けること・CMSに移植しやすいことを優先する。

```
<lp-name>/
├── index.html              … ページ本体
├── assets/
│   ├── css/style.css       … :root の変数に配色を集約
│   ├── js/main.js          … フェードイン／フォーム制御（ライブラリ不要）
│   └── img/                … SVG・写真
├── preview.html            … 1ファイル版（生成物）
├── tools/build-preview.py  … preview.html を作る
└── README.md               … 差し替え箇所・公開手順・原稿の注意
```

`preview.html` は CSS・JS・画像をすべて埋め込んだ1ファイル版。
**ダブルクリックで開ける**ので、クライアントにメールで直接渡す手段としても、
暗号化して公開する材料としても使う。`scripts/build-preview.py` を `tools/` に置いて生成する。

### A-3. 設計の基準

**配色は `:root` の変数に集約する。** ブランドカラーが後から確定しても、数値の差し替えだけで全体に反映できる。

```css
:root {
  --c-primary: #23415f;      /* 主色 */
  --c-primary-dark: #17304a;
  --c-accent: #b87a44;       /* CTA・アイコン */
  --c-accent-pale: #fbf1e4;
  --c-cream: #fbf8f3;        /* セクション交互の背景 */
  --c-text: #3a3630;
  --font: "Noto Sans JP", sans-serif;
  --font-serif: "Noto Serif JP", serif;
}
```

見出しに明朝、本文にゴシックを当てると、誠実さと読みやすさが両立しやすい。
Google Fonts が読めない環境でも崩れないよう、ヒラギノ・游ゴシック等のフォールバックを必ず並べる。

**シニア層が読者に含まれるなら**（相続・介護・保険・葬祭・不動産などはほぼ該当）：

- 本文 17px 前後、行間 1.9〜2.0
- 本文色と背景のコントラスト比 7:1 以上
- CTAのタップ領域を大きく取り、**スマホでは下部に追従バー**（電話／フォーム）を常時出す
- `prefers-reduced-motion` でアニメーションを止める

**セクションの背景は白→淡色→白と交互にする。** 同色が隣り合うと境目が消える。
セクションを1つ挿入したら、前後の背景色の並びを見直すこと。

**画像は元解像度を超えて引き伸ばさない。** 支給素材は小さいことが多い。
表示幅が元画像より大きくなるならレイアウト側（列幅・最大幅）で調整する。
横長素材を縦長の枠にはめようとすると破綻するので、**素材の縦横比に合わせて列比率を変える**。

### A-4. フォントのライセンス

**`lp-font-license` スキルを読むこと。** 内容はそちらに集約してある。

要点だけ挙げると、ロゴは支給されたラスター画像を流用してフォントで組み直さない、
Webフォントは SIL OFL のもの（Noto 等）だけにする、Monotype 系は名前すら出さない、
ブラウザ標準で `html` が Times New Roman・フォーム部品が Arial になるので上書きする、
Canva等の素材は必ず PNG/JPG で受け取る、納品前に `audit-fonts.js` を通す。

**フォントは着手時点で決めておく。** あとから差し替えると字幅が変わり、
行数がずれてレイアウトを組み直すことになる。

### A-5. 原稿の注意

制作物が広告である以上、書けないことがある。気づいたら黙って直さず、必ず伝える。

- **景品表示法**：「追加料金一切なし」「最短即日」「業界最安」などは、実運用と一致していなければ不当表示になる。
  企画書にあっても、**実際にそう運用しているかの確認を促す**。
- **買取・古物**：買取をうたうなら古物商許可番号の表示が必要。
- **医療・医薬品・化粧品**：効果効能の断定を避け、「個人差があります」を併記する。
- **事例・お客様の声**：企画書の想定値をそのまま載せると、実績と食い違う。
  READMEに「掲載前に実績と照合すること」を明記する。

### A-6. 検証（省略しない）

目視だけで済ませず、実際にブラウザで開いて確かめる。`references/verify.md` に手順と
そのまま使えるスクリプトがある。最低限、次を確認する。

- PC（1280px）／タブレット（900px）／スマホ（390px）でのスクリーンショット
- **横スクロールが出ていないか**（`scrollWidth > clientWidth` を数値で確認）
- 画像の `naturalWidth` が 0 でないか（パス切れの検出）
- フォームの必須チェックと送信時の挙動
- JSエラーの有無

過去に実際に見つかった不具合：アイコンにサイズ指定がなく巨大化、濃色背景に濃色文字で見出しが不可視、
`.u-sp-only` がボタンの `display` に負けてPCにも表示、CTAが折り返してファーストビューから押し出される。
**どれもスクリーンショットを見て初めて分かるもの**なので、必ず目で確認する。

### A-7. READMEに書くこと

引き継ぎのために、次を必ず残す。

- ダミー値の一覧表（項目／現在の値／出現箇所）と、一括置換コマンドの例
- フォームの送信先が未設定であること、`action` を設定すれば通常送信に切り替わること
- `noindex` を入れてあること、**本番公開時に削除が必要**であること
- 料金・事例・お客様の声の出どころ
- 配色変数の一覧

## B. 確認用公開（パスワード付き）

### B-1. 方式の前提

**GitHub Pages には標準のパスワード機能がない。** アクセス制限は GitHub Enterprise の機能で、
無料・Proでは使えない。そこで、**ページ本体を暗号化して置く**。

- 公開リポジトリには `index.html`（パスワード入力画面）と `site.bin`（暗号化したLP）だけを置く
- 正しいパスワードを入れたときだけ、ブラウザの中で復号してLPが表示される
- `site.bin` を直接ダウンロードしても、パスワードなしでは中身を取り出せない
  （AES-256-GCM／鍵は PBKDF2-SHA256 25万回）

平文のLPは**別リポジトリ（元データ側）**で管理する。この2リポジトリ構成が要で、
公開側に平文を置いてしまうと、パスワードをかけた意味がなくなる。

### B-2. 手順

1. **元データを push する**（制作用リポジトリ／サブフォルダでよい）

2. **公開用リポジトリを作ってもらう。**
   リポジトリの作成APIは権限エラー（403 Resource not accessible by integration）になることが多いので、
   ユーザーに作ってもらう。手順は次の通り伝える。

   - <https://github.com/new> を開く
   - Repository name を入力（**URLにそのまま出るので、案件が分かる短い名前**にする。
     他案件のリポジトリに間借りすると、無関係な名前がURLに出てしまう）
   - **Public** を選ぶ（Private だと GitHub Pages が使えない）
   - **README・.gitignore・ライセンスのチェックはすべてオフ**（空で作る。何か入っているとpushがぶつかる）

3. **作成後、セッションに追加して clone する**

   ```
   add_repo(owner, repo, access="push")
   git clone --depth 1 https://github.com/<owner>/<repo> /home/user/<repo>
   ```

4. **暗号化して配置する**

   ```bash
   python3 tools/build-preview.py                    # preview.html を作る
   node tools/build-encrypted.js <パスワード>         # preview.html → site.bin
   ```

   公開リポジトリに置くファイル：

   ```
   ├── index.html   … パスワード入力画面（assets/gate-template.html を案件用に書き換える）
   ├── site.bin     … 暗号化したLP
   ├── robots.txt   … User-agent: * / Disallow: /
   └── .nojekyll    … GitHub Pages がファイルをそのまま配信するための空ファイル
   ```

5. **平文を履歴に残さない。**
   先に平文をpushしてしまった場合、ファイルを消すだけでは**コミット履歴から読めてしまう**。
   `git checkout --orphan` で履歴を作り直して force push する。
   自分が直前に作ったコミットだけが対象なら安全だが、**実行前に必ずユーザーに伝える**。

6. **Pages を有効にしてもらう**
   Settings → Pages → Deploy from a branch → `main` ／ `/ (root)` → Save。
   1〜2分で `https://<owner>.github.io/<repo>/` が公開される。

7. **URLとパスワードをユーザーに渡す。** あわせて次を伝える。
   - 検索結果には出ないが、**URLを知っていれば誰でもアクセスできる**（パスワード画面までは見える）
   - ダミーのままの項目（電話番号など）があれば、クライアントに見せる前に判断が必要なこと
   - 確認が終わったらリポジトリを削除するか、Pagesを止めること

### B-3. パスワードや内容を変えるとき

元データ側で直し、`site.bin` を作り直して公開リポジトリに置き換えて push するだけ。
`index.html`（パスワード画面）は触らなくてよい。

```bash
python3 tools/build-preview.py
node tools/build-encrypted.js <新しいパスワード>
# できた site.bin を公開リポジトリにコピーして push
```

パスワードを変えたら、**クライアントへの再連絡が必要**であることを必ず添える。

## C. 呼び出し（既存LPを直す）

新しいセッションでは、過去に作ったLPはローカルにない。GitHubから取り出す。

### C-1. どのリポジトリか分からないとき

```
mcp__github__search_repositories(query="user:<owner>", minimal_output=true)
```

でアカウントのリポジトリ一覧を出し、名前から当たりをつけてユーザーに確認する。
`<案件名>-lp` と `<案件名>-lp-preview` のように、**元データ側と公開側で2つある**ことが多い。
直すのは**元データ側**（平文があるほう）。

### C-2. 取り出す

```
add_repo(owner, repo, access="push")     # 書き換えて push するので push 権限で
git clone --depth 1 https://github.com/<owner>/<repo> /home/user/<repo>
```

サブフォルダ運用（`<repo>/<lp-name>/`）のこともあるので、`ls` で構造を確かめる。
ブランチが `main` でないこともある。`git branch -a` で確認する。

### C-3. 直して戻す

修正 → `references/verify.md` の手順で検証 → commit → push。
確認用ページも公開しているなら、**B-3の手順で `site.bin` も作り直す**。
元データだけ直して公開側を忘れると、クライアントには古いページが見え続ける。

### C-4. 素材が手元にないとき

会話に貼られただけの画像は、ファイルとして保存されていないことがある。
その場合はセッションのログから取り出せる。

```
/root/.claude/projects/<project>/<session-id>.jsonl
```

各行のJSONを走査し、`{"type":"image","source":{"media_type":..., "data": <base64>}}`
を探してデコードすれば復元できる。取り出したら元データ側の `assets/img/` に保存する。

## 同梱物

| ファイル | 用途 |
| --- | --- |
| `scripts/build-preview.py` | `index.html` + `assets/` → 1ファイル版 `preview.html` |
| `scripts/build-encrypted.js` | `preview.html` → 暗号化した `site.bin` |
| `assets/gate-template.html` | パスワード入力画面の雛形。`{{ }}` の箇所を案件に合わせて書き換える |
| `scripts/audit-fonts.js` | フォントのライセンス監査。納品前に必ず通す |
| `references/verify.md` | ブラウザ検証の手順と、そのまま使えるスクリプト |

`scripts/` の2つは案件の `tools/` にコピーして使う。README にもコマンドを書いておくと、
別のセッションで再開したときに迷わない。
